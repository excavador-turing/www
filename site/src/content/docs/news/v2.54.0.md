State changes now need POST or a token, `tpi` verifies the board's certificate against a one-time pin, logout revokes the token, backups no longer carry secrets, and firmware upload and login are safer. Before you update: pin a self-signed board once with `tpi --pin` (or use `--insecure`), move scripts that change state with GET and Basic auth to POST or a Bearer token, run BMC-UI 4.8.0 or newer if the interface is served apart from the board, and let on-board scripts use `/run/bmcd/local-token`. Thank you, Daniel Steinhauf ([@danste22](https://github.com/danste22)), for a careful security review of the BMC and for the fixes across bmcd, tpi, BMC-UI and the firmware.

##### Upgrading

Four things change for whatever talks to a board. The details are under
"Breaking changes".

1. **Workstation `tpi` 2.0.0 verifies certificates.** Pin a self-signed board
   once with `tpi --host <board> --pin <sha256>` (or `TPI_PIN`), or use
   `--insecure`.
2. **Scripts that change state with GET and Basic auth must switch to POST or a
   Bearer token.** GET with a Bearer token still works in this release only.
3. **A web UI served separately from the board** (for example behind a reverse
   proxy) **must be BMC-UI 4.8.0 or newer**, because state changes now need
   POST.
4. **On-board scripts reach the API with `/run/bmcd/local-token`**
   (`Authorization: Bearer $(cat /run/bmcd/local-token)`).

##### Breaking changes

- **tpi 2.0.0 checks the board's certificate** (tpi#21, #27). A self-signed
  board is refused until you tell tpi which certificate is yours, once per
  board: run any command, compare the fingerprint it prints with the board's
  own (BMC-UI, Security, Certificates, or `openssl x509 -in
  /etc/ssl/certs/bmcd_cert.pem -noout -fingerprint -sha256` on the serial
  console), then run once with `--pin <fingerprint>` (or `TPI_PIN`). `--insecure`
  (or `TPI_INSECURE=1`) skips the check, for a lab. On the board itself,
  `tpi` still skips the check for `127.0.0.1` and `::1`, and only for those:
  `--host localhost` is a name, not a loopback address, and is verified like
  any other host. Use `--host 127.0.0.1` or no `--host`.
- **Scripts on the board need the local token** (bmcd 2.48.0, bmcd#72/#77).
  The loopback exemption is gone: a request from `127.0.0.1` with no credential
  answers 401. At every start bmcd writes a 64-character token to
  `/run/bmcd/local-token` (directory 0700, file 0600) and accepts it as a
  Bearer token from a loopback peer only:
  `Authorization: Bearer $(cat /run/bmcd/local-token)`. The on-board `tpi` does
  this by itself for `127.0.0.1` and `::1` when no credentials are given. The
  firmware's own scripts were checked: the promotion gate asks for the static
  page at `https://127.0.0.1/` and for `/metrics` on port 9110, neither of which
  is the API, and no script calls the API otherwise.
- **A state change over GET needs a Bearer token** (bmcd#72 through #77). Every
  `opt=set` type on `/api/bmc`, the upload cancel and the backup are POST now.
  Their GET forms are served for one more release, with a Bearer token only, so
  older `tpi` and BMC-UI keep working; with Basic or no credential they answer
  405 with `Allow: POST`. Scripts should use `curl -X POST`. tpi 2.0.0 and
  BMC-UI 4.8.0 send POST, and fall back to GET on a 405 from an older board.
- **A firmware file name must be one safe path component** (bmcd#64). A `file`
  outside `[A-Za-z0-9._-]`, or `.` or `..`, is refused with 400 for
  `type=firmware`; a browser download named `tp2-bmc-firmware (1).tpu` has to be
  renamed first.
- **The login body is capped** (bmcd#65): over 4 KiB answers 413, and one that
  is not complete within 5 seconds answers 408.
- **Basic is refused on a browser's request, and a cross-site state change
  answers 403** (bmcd#72 through #77). A request that carries `Origin`,
  `Referer` or `Sec-Fetch-*` and authenticates with Basic is refused; a state
  change whose `Sec-Fetch-Site` is `cross-site` or `same-site` is refused
  whatever the credential.
- **A password change ends every session, the caller's included** (bmcd#72).
  BMC-UI tabs and cached `tpi` tokens sign in again. `POST /api/bmc/logout`
  revokes just the token that sends it, and BMC-UI 4.8.0 uses it on logout.
- **A backup no longer holds secrets** (bmcd#72). It leaves out `etc/shadow*`,
  `etc/gshadow*`, every `.pem` or `*key*` under `etc/ssl`, and the SSH host
  keys. A restore only writes what the archive holds, so the board it goes back
  onto keeps its own password, certificate and host keys.
- **HTTP/2 is gone** (bmcd#71 through #78). Browsers and `curl` are unaffected;
  `curl --http2-prior-knowledge` fails.
- **tpi caches its login token per board**, mode 0600, and sends it only back to
  the board that issued it (tpi#22, #29). Log in once again after the update. A
  failed `tpi flash` now exits 1 (tpi#24, #30).
- **A flash starts about one second later** (bmcd#74). A node that was running
  is held off for one second before it is switched on to flash; a node that had
  not powered down in a fraction of a second never read the USB boot pin.

## New

### The release carries a `SHA256SUMS` file beside the archives and packages; check a download with `sha256sum -c SHA256SUMS --ignore-missing`
<small class="tp-tag">tpi 2.0.0</small>

The release workflow no longer uses the archived `actions-rs` actions, and every action is pinned by commit.


## Changed

- **bmcd 2.48.0.** Is a security release.

    <details class="note">
    <summary>The whole entry</summary>

    A caller-chosen firmware name no longer reaches a shell (`osupdate` runs with the path as one argument); login no longer holds the one authentication lock while the body is read or the password is hashed; the UI sends `frame-ancestors 'none'`, `nosniff` and `X-Frame-Options: DENY`; the serial history leaves the unsound ring buffer. A switch command no longer blocks a worker, and a client that goes away mid-change no longer lets the next one interleave; a stopped firmware copy deletes its staging directory; the shadow watcher no longer panics or stops; a persistency value that cannot be read or written is an error the API reports. (bmcd#64, #65, #66, #70 through #78.) The release profile change in bmcd#78 does not reach the board: Buildroot overrides the cargo release profile.

    </details>

- **tpi 2.0.0.** Verifies the board's certificate and remembers its key per host, keeps the cached token private, aborts a non-ASCII password edit, sends state changes as POST and uses the board's local token on loopback.

    <details class="note">
    <summary>The whole entry</summary>

    It is built on reqwest 0.13 with ring, and its releases carry a `SHA256SUMS`.

    </details>

- **BMC-UI 4.8.0.** The power switch waits for the board's answer, a change made offline fails at once, logout revokes the token on the board, a failed node flash or firmware upload no longer logs an unhandled promise, and the backup is taken only if the answer is a gzip archive.

    <details class="note">
    <summary>The whole entry</summary>

    Building needs Node 26. (BMC-UI#62 through #65.)

    </details>

- **bmcd 2.48.0, tpi 2.0.0 and BMC-UI 4.8.0.** Are the pinned versions (the latest of each).
- **CI reports advisories on their own.** `cargo deny check advisories` runs in a job of its own that reports and does not block pull requests, plus a weekly run on `hive` that does fail, so a new RUSTSEC entry no longer turns every pull request red. <small class="tp-tag">bmcd 2.48.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    `deny.toml` lists the advisories that are known, each with its reason (actix-files RUSTSEC-2026-0443, Windows short names only; bincode RUSTSEC-2025-0141, waiting for a reader of the existing `bmcd.bin`; chrono RUSTSEC-2026-0543, unmaintained, not vulnerable). (#78)

    </details>

- **The release profile is fat LTO with one codegen unit.** (it was thin LTO with 16), which makes the armv7 binary about 21 % smaller (11,185,280 to 8,777,724 bytes, stripped). <small class="tp-tag">bmcd 2.48.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    Buildroot overrides the release profile for every cargo package (`CARGO_PROFILE_RELEASE_LTO=false`, 16 codegen units, `opt-level` 2), so the board image does not get the smaller binary from this change; that needs a separate firmware change. (#78)

    </details>

- **The tests use `tempfile` instead of `tempdir`.** Which also drops `remove_dir_all` from the dependency tree. (#78) <small class="tp-tag">bmcd 2.48.0</small>
- **Breaking: `tpi` verifies the board's certificate.** The client used to accept any certificate, so a peer answering to the board's name received the password and the token. <small class="tp-tag">tpi 2.0.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    A self-signed board is now accepted once its SHA-256 fingerprint is given with `--pin` (or `TPI_PIN`), after you compared it with BMC-UI (Security, Certificates) or the board's console. tpi then remembers the board's public key per scheme, host and port, so a renewal that keeps the key keeps the pin. `--insecure` (or `TPI_INSECURE`) skips the check. Every existing script needs one pin per board. The localhost build skips only for `127.0.0.1` and `::1`. ([#21](https://github.com/excavador-turing/tpi/pull/21), carried on as [#27](https://github.com/excavador-turing/tpi/pull/27))

    </details>

- **A refused certificate prints the endpoint, the fingerprint it presented,
where to compare it, the command to pin it and the pin file.** A changed key shows both fingerprints. Every error prints its whole cause chain. <small class="tp-tag">tpi 2.0.0</small>
- **A stored pin is strict and wins over a CA-signed chain.** Deleting its file, whose path the refusals print, forgets it. <small class="tp-tag">tpi 2.0.0</small>
- **Breaking: the login token is cached per board.** One file per `scheme://host:port`, mode 0600, in a directory mode 0700, and sent only back to the host that issued it. After the update you log in once again, per board. <small class="tp-tag">tpi 2.0.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    Over plain `http` no token is kept or sent, so the password is asked on every call. The old shared `tpi_token` is removed. ([#22](https://github.com/excavador-turing/tpi/pull/22), carried on as [#29](https://github.com/excavador-turing/tpi/pull/29))

    </details>

- **State changes go as POST.** A board that answers 405, an older bmcd, gets the identical request once more as GET. <small class="tp-tag">tpi 2.0.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    The localhost build (the one on the board) sends the board's own token, `/run/bmcd/local-token`, to `127.0.0.1` or `::1` when no credentials are given; a name such as `localhost` is not enough. ([#26](https://github.com/excavador-turing/tpi/pull/26), carried on as [#31](https://github.com/excavador-turing/tpi/pull/31))

    </details>

- **tpi is built on reqwest 0.13 with the ring crypto provider, as before; unused
crates are gone, `cargo deny` also checks advisories, and the release
binaries are size-optimised.** ([#25](https://github.com/excavador-turing/tpi/pull/25), carried on as [#28](https://github.com/excavador-turing/tpi/pull/28)) <small class="tp-tag">tpi 2.0.0</small>
- **The power switch waits for the board's answer.** ([#62](https://github.com/excavador-turing/BMC-UI/pull/62), BMC-Firmware#97). The switch moved, toasted success and closed its dialog before the board had answered, so a refused change looked like a success. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    The switch, the toast and the dialog now follow a successful answer; a refusal puts the switch back and shows the board's message. A failed change is reported once, by the query client, in the board's own words (in the fleet the toast names the board), and the USB page no longer toasts a failure twice.

    </details>

- **A change made offline fails at once.** (#62). TanStack Query held a change while the browser reported itself offline and sent it when it came back, possibly minutes later, when nobody asked for it any more. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    It is sent straight away now, and fails straight away.

    </details>

- **Logout ends the token on the board.** ([#64](https://github.com/excavador-turing/BMC-UI/pull/64), BMC-Firmware#100). Signing out used to clear the browser's storage and leave the token valid until it expired, so a copy of it kept working. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    It now sends `POST /api/bmc/logout` first, and clears the session whatever the answer, so an older board (404 or 405) or one that cannot be reached still signs the user out. A 401 clears the session without asking the board, which is what follows a password change. This needs a bmcd with the logout route ([bmcd#72](https://github.com/excavador-turing/bmcd/pull/72)); against an older one it signs out locally.

    </details>

- **Building needs Node 26.** ([#63](https://github.com/excavador-turing/BMC-UI/pull/63), BMC-Firmware#95). `.nvmrc` and `devbox.json` move from Node 24 to 26, and so do `Dockerfile.fleet` (`node:26-alpine`), `devbox.lock` and the README. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    The built interface behaves the same. `npm audit fix` refreshes the lockfile, and i18next goes to 27 and react-i18next to 18.

    </details>


## Fixed

- **The board keeps its TLS key when it renews its own certificate.** ([#108](https://github.com/excavador-turing/BMC-Firmware/pull/108), by [@danste22](https://github.com/danste22); BMC-Firmware#90).

    <details class="note">
    <summary>The whole entry</summary>

    A renewal 30 days before expiry and a reissue after a rename both made a new key, so every renewal would have broken the pin tpi 2.0.0 keeps. Both paths now sign the new certificate with the key already on disk; a new key is made only when there is none or the key is not the certificate's own. The SHA-256 of the certificate changes, the key does not. A board whose key must be replaced needs `/etc/ssl/certs/bmcd_key.pem` deleted before the generator runs.

    </details>

##### Tested

- **On both of our v2.5 boards with v2.54.0-rc.1: the over-the-air update; a BMC
reboot adopts the live power state with no node reset; the on-board `tpi`
works without a password; the API refuses unauthenticated loopback calls; the
TLS key is unchanged across a reboot; the fleet UI works through a gateway.**
- **A switch command no longer blocks a worker, and a client that goes away
mid-change no longer lets the next one interleave.** `ip` and `bridge` ran on an async worker while the switch lock was held; they now run on a blocking thread, and the lock is not held across the wait. <small class="tp-tag">bmcd 2.48.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    The turn that makes switch changes one at a time now travels with the commands rather than with the request: when a client disconnected in the middle of an apply or a revert, the turn was released while the commands kept running, the next change could interleave, and the running configuration was never recorded. Now the change finishes and records itself, and the next one waits. Reading the switch back from the kernel after a failed apply also runs on a blocking thread. (#70 through #76, BMC-Firmware#96)

    </details>

- **A firmware copy that stops deletes its staging directory.** (#76) <small class="tp-tag">bmcd 2.48.0</small>
- **The shadow watcher no longer panics or stops.** When the file is replaced or the watch fails it builds the watch again with backoff and reloads, so password changes keep being noticed. (#76) <small class="tp-tag">bmcd 2.48.0</small>
- **A persistency value that cannot be read or written is an error the API
reports.** Instead of a panic or a silent default; only the console speeds at startup fall back to 115200, with the error logged. (#76) <small class="tp-tag">bmcd 2.48.0</small>
- **A failed `tpi flash` exits 1.** It exited 0 when the flash did not finish. ([#24](https://github.com/excavador-turing/tpi/pull/24), carried on as [#30](https://github.com/excavador-turing/tpi/pull/30)) <small class="tp-tag">tpi 2.0.0</small>
- **Editing a non-ASCII character at the password prompt no longer panics, and
Ctrl+C at the prompt aborts instead of returning what was typed.** A 401 is retried once, and not after an upload body was sent. <small class="tp-tag">tpi 2.0.0</small>
- **The lockfile is refreshed inside the current requirements.** ([#23](https://github.com/excavador-turing/tpi/pull/23)) <small class="tp-tag">tpi 2.0.0</small>
- **A failed node flash or firmware upload no longer also logs an unhandled
promise.** ([#65](https://github.com/excavador-turing/BMC-UI/pull/65), BMC-Firmware#110). The failure was reported (the progress panel and the toast) and then surfaced a second time as `Uncaught (in promise)` in the console. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    Nothing visible changes but the console error.

    </details>

- **A backup from an older board is never a page.** On a board older than bmcd#72 a POST to `/api/bmc/backup` does not get a 405: the daemon routes the backup on GET only, so the request fell through to the interface's own page and was answered 200 with `index.html`, which the new POST would have saved as `tp2-backup-....tar.gz`. <small class="tp-tag">BMC-UI 4.8.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    The backup now accepts the POST answer only if it is a gzip archive and otherwise asks again with GET; if what comes back still is not an archive, the button reports an error instead of saving it. This is our fix on top of #64.

    </details>


## Security

### A caller-chosen firmware name no longer reaches a shell
<small class="tp-tag">bmcd 2.48.0</small>

It was joined onto the staging directory and interpolated into `sh -c`, so an absolute path or `../` wrote outside it and shell characters in a URL's last segment became part of the command.

<details class="note">
<summary>The whole entry</summary>

`osupdate` now runs with the path as one argument and no shell. (#64, BMC-Firmware#88)

</details>

### Logging in no longer holds the one authentication lock while the body is read or the password is hashed
<small class="tp-tag">bmcd 2.48.0</small>

The login handler held it across an unbounded read and a `sha512_crypt`; the body is now read first (see the cap above), the hash is checked on the blocking pool without the lock, and the lock is taken again only to update the session map.

<details class="note">
<summary>The whole entry</summary>

Basic is split the same way, and the middleware no longer holds the lock while the route runs. A stored hash that `crypt` cannot read is a check failure, not a wrong password. (#65, BMC-Firmware#89)

</details>

### A page on another site can no longer change the board through the browser's stored Basic credentials
<small class="tp-tag">bmcd 2.48.0</small>

And the UI responses send `frame-ancestors 'none'`, `nosniff` and `X-Frame-Options: DENY`. (#72 through #77, BMC-Firmware#99)

### The serial history is off the unsound ring buffer
<small class="tp-tag">bmcd 2.48.0</small>

`circular-buffer` 0.1 can leave its pointers on uninitialised memory if a drop panics; the serial log uses the 2.0 fixed buffer.

<details class="note">
<summary>The whole entry</summary>

`humantime` (unmaintained, RUSTSEC-2026-0542) is replaced by a small formatter, and the lockfile is refreshed inside the current requirements, so the patched crates are in. (#71 through #78, #66; BMC-Firmware#93, #91)

</details>
