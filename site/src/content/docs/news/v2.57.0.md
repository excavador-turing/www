A percent-encoded path such as `/api/b%6dc` no longer slips past the refusal of a state change over GET and the cross-site refusal (it is now a 400), the file that holds the power state is flushed to flash before it is renamed into place, so a power cut cannot leave the daemon on default storage, and the serial console WebSocket refuses a handshake opened from another site. Nothing to do on a board or in a script. The release also carries the RK1 flash path on `rockusb` 0.4 and checksums built for speed, `tpi` 2.0.1 and BMC-UI 4.8.1, where the selected node stays readable on hover. Thank you, adberger ([@adberger](https://github.com/adberger)), for [#132](https://github.com/excavador-turing/BMC-Firmware/issues/132) and [#130](https://github.com/excavador-turing/BMC-Firmware/issues/130), and Daniel Steinhauf ([@danste22](https://github.com/danste22)) for the RK1 flash path, the `opt-level` suggestion and the `tpi` clean-up.

Firmware **v2.57.0**, 25 November 2026. Every item below is the repository's own changelog entry, taken apart; the whole entry is a click away under each one.

Pins **bmcd 2.50.2** (v2.55.0 had 2.49.0), **tpi 2.0.1** (2.0.0) and **BMC-UI
4.8.1** (4.8.0). The kernel stays at 6.18.63. Three security fixes in the
daemon (two reported by adberger), the RK1 flash path moves to `rockusb` 0.4,
the hashing and checksum loops are built for speed, and the console node picker
is readable under the pointer. There is nothing to do on a board or in a script: no
behaviour a client relies on changes.

Thanks to adberger ([@adberger](https://github.com/adberger)) for

and

Thanks to Daniel Steinhauf ([@danste22](https://github.com/danste22)) for

##### Upgrading

Nothing changes for whatever talks to a board: scripts, `tpi` 2.0 and BMC-UI 4.8
keep working as they did with v2.55.0. A client that percent-encodes the path of
an API request (no client we know of does) now gets 400.

## Changed

- **The RK1 flash path uses `rockusb` 0.4.** (bmcd 2.50.0, bmcd#85, step 3 of BMC-Firmware#93).

    <details class="note">
    <summary>The whole entry</summary>

    `rockusb` 0.2.0 to 0.4.0 is the library that puts an RK1 (RK3588) into USB download mode and loads its SPL loader before the eMMC is written; the bytes it sends are the same. Written by Daniel Steinhauf, who flashed an RK1 three times with it on a board (our own RK1s all run a live cluster, so we did not reflash one for this). Its new crates (`maybe-async-cfg` and the proc-macro crates it builds with, `strum` 0.28) all come from crates.io and passed `cargo deny`. The RK1 flash path is tested by him, not by us.

    </details>

- **`sha2`, `crc` and `crc32fast` are built at `opt-level = 3`.** (bmcd 2.50.0, bmcd#86, suggested by Daniel Steinhauf in BMC-Firmware#93).

    <details class="note">
    <summary>The whole entry</summary>

    The rest of bmcd stays at `"z"`; these three run the per-byte loops of a flash (the SHA-256 of the image, the CRC-64 of what is written to the node, the CRC-32 of the board EEPROM) and cost a few KB. Since #117 the daemon is built to its own `[profile.release]`, so this is what reaches the image.

    </details>

- **The token and certificate-pin file helpers exist once in `tpi`.** (tpi 2.0.1, tpi#33, BMC-Firmware#115). A refactor by Daniel Steinhauf with no change in behaviour: the same files, paths and modes.
- **BMC-UI 4.8.1: the selected node stays readable on hover.** (BMC-UI#69). In the node picker of the Console, Flash Node and USB pages, hovering the selected segment turned its text to the page colour, dark on dark in the light theme and light on light in the dark theme.

    <details class="note">
    <summary>The whole entry</summary>

    It keeps its own colours now.

    </details>

##### Tested

- **On two Turing Pi 2 v2.5 boards, eight compute nodes, with v2.57.0-rc.2
(2026-11-24): both boards updated over the network, board B first, then board
A; every gate passed and no compute node lost power.** A BMC reboot adopts the live power state, the switch VLAN configuration is unchanged and the power latch shadow is valid.
- **The security fixes, on the hardware:
- a percent-encoded path under `/api/bmc` (`/api/b%6dc`) answers 400;
- the serial console WebSocket handshake answers 403 when `Sec-Fetch-Site` is
  `cross-site` or `same-site`, and 403 for a foreign `Origin`;
- it answers 101 (the socket opens) when `Origin` equals the `Host`, and 101
  with no `Origin` at all (`tpi`, `curl`);
- a state change sent as GET answers 405 with `Allow: POST`, while the same
  change sent as POST works.**
- **The serial console connects in a browser (confirmed 2026-11-25).**
- **Components in the image: bmcd 2.50.2, tpi 2.0.1, BMC-UI 4.8.1.**
- **BMC-UI 4.8.1: the selected node stays readable on hover (confirmed in a
browser).**
- **Response times did not change with the earlier v2.56.0 pre-release: about
0.135 s per request on the board.**
- **The RK1 flash path (`rockusb` 0.4) was tested by Daniel Steinhauf
([@danste22](https://github.com/danste22)), three flashes on an RK1.** Our eight RK1s all run a live cluster, so we did not reflash one to test it.
- **The speed of a node flash's checksums was not measured by us.** The three checksum crates are built at full speed; everything else is unchanged.

## Security

### A percent-encoded path no longer slips past the GET and cross-site refusals

(bmcd 2.50.1, bmcd#90, Refs #132, reported by adberger).

<details class="note">
<summary>The whole entry</summary>

The daemon's refusal of a state change over GET or HEAD (405) and of a cross-site one (403) read the raw request path, while the router matches the decoded one, so spellings such as `/api/b%6dc` reached the same handlers without either refusal. Authentication still applied; what was lost is the protection for a credential the browser attaches by itself (a client certificate, a trusted proxy's identity header). The policy now reads the path the router matched, a request under `/api/bmc` with percent-encoding in its path is refused with 400, and the `?opt=set` handler itself refuses GET and HEAD.

</details>

### `bmcd.bin` is replaced durably

(bmcd 2.50.1, bmcd#89, Refs #130, reported by adberger).

<details class="note">
<summary>The whole entry</summary>

The store of the power state, USB mode and node information was renamed into place without flushing its data, so a power cut on UBIFS could leave bmcd starting on new, default storage. It is written through `write_durably` now: data flushed before the rename, directory after.

</details>

### The serial console WebSocket refuses a handshake opened from another site

(bmcd 2.50.2, bmcd#93, found in our own review). The console reads and writes a node's UART.

<details class="note">
<summary>The whole entry</summary>

A handshake is a `GET`, so the cross-site refusal for state changes did not see it, and a browser does not hold a WebSocket to the same-origin policy. Behind a reverse proxy that authenticates with a client certificate the browser sends no token of its own, so a page on another site could open the console; directly on the board it was not reachable this way. A handshake whose `Sec-Fetch-Site` is not `same-origin` or `none` is now 403, and without that header one whose `Origin` is not the `Host`. `tpi`, `curl` and BMC-UI, which opens the socket on its own host, are served as before.

</details>
