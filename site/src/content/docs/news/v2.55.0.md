Breaking: a request that changes state over GET now answers 405 with `Allow: POST`, a Bearer token included. Scripts must use `curl -X POST`, a workstation `tpi` must be 2.0 or newer, and a web UI served apart from the board must be BMC-UI 4.8.0 or newer. The interface is also served with a Content-Security-Policy, and `bmcd` and `tpi` are built to their own release profile, so the daemon shrinks from 14.3 to 9.1 MB and `tpi` from 5.0 to 2.8 MB. Thank you, Daniel Steinhauf ([@danste22](https://github.com/danste22)), for the issue ([#109](https://github.com/excavador-turing/BMC-Firmware/issues/109)), the fix ([bmcd#73](https://github.com/excavador-turing/bmcd/pull/73)) and the review that found the rest.

##### Upgrading

This is the release that ends v2.54.0's transition for state changes over GET.
Three things change for whatever talks to a board. The details are under
"Breaking changes".

1. **Scripts and integrations that change state with GET must use POST**
   (`curl -X POST`), with a Bearer token as before. A Bearer token no longer
   saves a GET: it answers 405 with `Allow: POST`.
2. **A workstation `tpi` must be 2.0 or newer.** Older `tpi` sends GET for a
   state change and is refused. `tpi` 2.0.0 sends POST (and still needs its
   one-time `--pin` for a self-signed board, see v2.54.0).
3. **A web UI served separately from the board** (for example behind a reverse
   proxy) **must be BMC-UI 4.8.0 or newer**. The one this firmware ships is
   4.8.0. A custom `www` bundle that needs an inline script or an external host
   has to be built to the new Content-Security-Policy.

##### Breaking changes

- **Every state change over GET is refused, whatever the credential** (bmcd
  2.49.0, bmcd#73/#83, BMC-Firmware#109). v2.54.0 still served the GET forms of
  a state change (every `opt=set` type, the upload cancel and the backup) with a
  Bearer token, so that older clients kept working. That transition is over:
  those requests answer 405 with `Allow: POST`, with a Bearer token, with Basic
  or with none. A workstation `tpi` must be 2.0 or newer, a separately served
  BMC-UI must be 4.8.0 or newer (the BMC-UI this firmware ships is 4.8.0), and
  scripts must use `curl -X POST`. The backup, the cancel and the transfer are
  routed on POST only, and the OpenAPI document no longer lists their GET forms.

## Changed

- **bmcd and tpi are built with their own release profile.** Buildroot's cargo infrastructure sets `CARGO_PROFILE_RELEASE_OPT_LEVEL`, `_LTO` and `_CODEGEN_UNITS` for every package, and environment variables outrank the manifest, so the `[profile.release]` of bmcd and tpi (fat LTO, one codegen unit, `opt-level = "z"`) never reached the image: both were built at `-O2` with no LTO and 16 codegen units.

    <details class="note">
    <summary>The whole entry</summary>

    `tp2bmc/external.mk` now unsets those three variables for the two packages, and the profile in their `Cargo.toml` decides. The build log also prints the installed size of both binaries. Spotted by Daniel Steinhauf ([@danste22](https://github.com/danste22)) in his review. Measured in two full CI builds of the same tree: `/usr/bin/bmcd` 14.3 MB to 9.1 MB (-36.5 %), `/usr/bin/tpi` 5.0 MB to 2.8 MB (-44.0 %); the build takes about four minutes longer. (#117) Refs [#93](https://github.com/excavador-turing/BMC-Firmware/issues/93).

    </details>

##### Tested

- **On two Turing Pi 2 v2.5 boards, eight compute nodes, with v2.55.0-rc.1
(2026-11-24): the update over the network with `tpi-selfupdate`; a BMC reboot
adopts the live power state with no node power-cycled; the switch VLAN
configuration is unchanged; the power latch shadow is valid.**
- **Every state change sent as GET answers 405 with `Allow: POST`, while the same
change sent as POST works.**
- **Response times do not change with the smaller build: about 0.13 s per request
on the board, the same as with v2.54.0-rc.1.**

## Security

### The web interface is served with a Content-Security-Policy

(bmcd 2.49.0, bmcd#81, BMC-Firmware#99). `script-src 'self'`, no inline script and no `eval`, so an injected `<script>` does not run, and a page cannot post a form elsewhere.

<details class="note">
<summary>The whole entry</summary>

It was written against the BMC-UI 4.8.0 bundle. Safari before 15.4 does not match a same-host WebSocket against `connect-src 'self'`, so the serial console needs Safari 15.4 or newer.

</details>

### Two dependency decisions are written down

(bmcd 2.49.0, bmcd#80, #82): the `cookie` 0.16 advisory is accepted because the affected code is not compiled in, and bincode 1 stays for `bmcd.bin` on purpose, each with its reason in `deny.toml`.

### RUSTSEC-2026-0594 (`cookie` 0.16, via actix-web) is accepted, with the reason in `deny.toml`
<small class="tp-tag">bmcd 2.49.0</small>

The advisory is AES-GCM nonce reuse in `PrivateJar::add` and `add_original` after `fork()`.

<details class="note">
<summary>The whole entry</summary>

That API exists only behind cookie's `private` feature, which actix-web does not enable (the lockfile has no `aes-gcm`), bmcd sets no cookies and authenticates with Bearer tokens, and the daemon does not fork. The fixed cookie 0.18.3 is out of reach: the newest actix-web (4.20.0) still requires `cookie ^0.16`. To be revisited when an actix-web release moves to a fixed cookie. Found by the weekly advisories job that Daniel Steinhauf ([@danste22](https://github.com/danste22)) asked for in BMC-Firmware#93. (#80)

</details>

### The interface is served with a script-restricting Content-Security-Policy
<small class="tp-tag">bmcd 2.49.0</small>

The UI responses carried only `frame-ancestors 'none'`; they now send `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, so an injected `<script>` or inline handler does not run and a page cannot post a form elsewhere.

<details class="note">
<summary>The whole entry</summary>

It was written against the BMC-UI 4.8.0 bundle: one module script and its chunks from the same origin, no inline script, no `eval`, no worker, fonts as files, and the API, the upload and the serial console WebSocket on the same host. `'unsafe-inline'` stays for styles only (the terminal and the theme switch add `<style>` elements). `connect-src 'self'` matches a same-host WebSocket in current browsers (Safari before 15.4 did not). The policy applies to the documents the board serves; when the interface is served by a fleet pod, that pod's policy governs the page and the board only answers API calls, which a CSP does not restrict. A custom `www` bundle that needs more (an external host, an inline script) has to be built to this policy. (#81, BMC-Firmware#99; found in the review by Daniel Steinhauf ([@danste22](https://github.com/danste22)).)

</details>

### bincode 1 stays for `bmcd.bin`, on purpose
<small class="tp-tag">bmcd 2.49.0</small>

See `deny.toml` (RUSTSEC-2025-0141). (#82)
