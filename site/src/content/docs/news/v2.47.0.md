A board's Firmware page used to say "Update available" and then list only old versions, and Upload .tpu could do nothing at all on a board without an SD card. The list now builds in 5 seconds instead of 170, the page keeps checking until it arrives, the badge installs the version it names, and Upload installs directly when there is no card.

<!-- more -->

Firmware **v2.47.0**, 1 November 2026 — the first image to carry [bmcd 2.42.2](/changelog/bmcd/), [BMC-UI 4.4.0](/changelog/bmc-ui/). Every item below is the repository's own changelog entry, taken apart; the whole entry is a click away under each one.

A community member on v2.44.0, with no SD card in the board, saw the badge say "Update available · v2.46.1" while the list below it showed only v2.44.0, v2.1.0 and v2.0.5. The subtitle stayed on "checking the sources now" with Check now greyed out until the page was reloaded, and uploading the v2.46.1 `.tpu` left "Next boot: nothing staged". Three things were wrong at once: the board took 170 seconds to build the fork's list of 44 releases (measured on 1 November 2026, on a Turing Pi 2 v2.5.1 board running v2.46.1), the page gave up after 120 seconds, and Upload could only park an image on an SD card the board did not have.

## How to get it if your Firmware page doesn't show it

A board running v2.46.1 or earlier still builds its list the slow way, so its own Firmware page may not list v2.47.0. Either of these gets you there.

Over SSH, on the BMC:

```console
$ ssh root@BMC 'tpi-selfupdate --tag v2.47.0 --reboot'
```

It downloads the release, verifies it against the published `SHA256SUMS`, stages it in the spare slot and reboots into it. The new image is kept only if it passes its health gate; if the daemon does not answer or a module's switch port is missing, the board reboots back onto the image it came from. Leave out `--reboot` to stage it and reboot when you choose.

Or wait about four minutes on the Firmware page and reload it: the board finishes building its list in the background and keeps it, so the second look is the full list. **A reboot of the BMC power-cycles the four compute modules on a Turing Pi 2 v2.4, so shut them down first; a v2.5 has a latch on each node's power rail and its nodes keep running.**

## New

### The "Update available" badge installs the version it names
<small class="tp-tag">BMC-UI 4.4.0</small>

It comes from the cheap update check, which knows of a release long before the list has it, so pressing it opens the same confirmation as the list's Install button.

<details class="note">
<summary>The whole entry</summary>

The confirmation says which source and repository it installs from and, when the list does not have the version yet, that too. The source is the GitHub source whose location is the repository the check named, and no other: another source listing the same version string does not count. If no configured source is that repository the badge is information only, with a line saying why. What the dialog shows is fixed when the badge is pressed and is what is sent, even if the list refreshes underneath; it never asks the updater to allow a downgrade unless the list says the version is older and the dialog says so. It is disabled while an install, an upload or a flash runs, or an update is already staged.

</details>

### The demo can show a board with no SD card and a list that is behind
<small class="tp-tag">BMC-UI 4.4.0</small>

`?card=none` is a board with no SD card (as bmcd 2.42.2 reports it), and `?firmware=stale` is a board running v2.44.0 whose update check offers v2.46.1 and whose list does not have it. Written changes to the captures, not captures.

## Fixed

- **New releases never appeared in the Firmware page's list on a board.** Listing the 44 releases of this repository took about three minutes on a real board (170 s for `tpi-selfupdate --list`, measured 2026-11-01 on v2.46.1), and the page stops waiting after two, so the list came back without the GitHub source and the newest releases were never shown. <small class="tp-tag">v2.47.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    `tpi-selfupdate` split the response on `},{`, which only exists in compact JSON; GitHub sends it pretty-printed (about 690 KB and 11,000 lines), so every line became its own piece and cost five forks, and the time grew with every release published. It is now one `awk` pass over the whole response (0.12 s against 6.1 s before on a workstation, same 44 releases), and the same pass now reads `prerelease`, which sits on a line the old code never looked at, so a pre-release is finally listed as one. Output and ordering are unchanged.

    </details>

- **The firmware page no longer gives up on a slow catalogue and sticks.** It now keeps asking while the daemon says it is refreshing, for up to eleven minutes, instead of two. <small class="tp-tag">BMC-UI 4.4.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    It backs off from every 2 s to every 5 s after 30 s and every 10 s after two minutes, and does not ask at all while the tab is hidden. If it does give up it says "Still checking — the list may be out of date. Reload later." and Check now works again; pressing it starts a fresh eleven minutes.

    </details>

- **Uploading a `.tpu` to a board with no SD card no longer fails with a toast and nothing else.** When the board has no card the dialog now says so and installs directly: written to the spare slot and staged for the next boot, confirmed with the same reboot warning as the Reboot button. <small class="tp-tag">BMC-UI 4.4.0</small>

    <details class="note">
    <summary>The whole entry</summary>

    With a card nothing changes: the image is parked and appears in the list. From bmcd 2.42.2 the Info storage list says whether the card is mounted (`mounted` on the "SD card" entry) and the dialog uses that exactly; before it, the dialog goes by whether that entry's size is the BMC's own volume. Where that is wrong, or unreadable, the daemon's refusal now stays in the dialog until dismissed, with "Install directly instead" beside it. A card that is not mounted is no longer drawn as a second storage row on the Info page nor given a usage line in the SD card picker. Upload errors in general persist in the dialog rather than only as a toast, and a finished upload refreshes the list and the slots panel, so "Next boot" shows what was staged.

    </details>

- **A board with no SD card kept retrying the whole firmware check every two minutes and showed a warning for it.** The `SD card` source answered "`/mnt/sdcard/firmware` is not a directory" as an error; a source on the card now reports nothing when the card is not mounted or has no `firmware` folder, and the catalogue is kept across a reboot. <small class="tp-tag">bmcd 2.42.2</small>

    <details class="note">
    <summary>The whole entry</summary>

    Any source error used to shorten the catalogue's cache from 30 minutes to 2 minutes and keep it off the overlay, so a card-less board never kept a good catalogue across a reboot. A card that is there and unreadable is still an error, and so is a card the kernel sees (`/dev/mmcblk0`) that nothing has mounted, which now says "an SD card is inserted but not mounted (unsupported or damaged filesystem?)". The response shape is unchanged.

    </details>

- **One hung firmware source discarded every other source's answer.** Each source now has its own 360 s deadline; a source that overruns reports `timed out after 360 s` as its own error, and the others are cached as usual. <small class="tp-tag">bmcd 2.42.2</small>

    <details class="note">
    <summary>The whole entry</summary>

    The refresh used to wait for all sources and was cut off as a whole after 10 minutes, so a stuck `curl` under `tpi-selfupdate --list` cost the fast sources their results too. The updater now runs in its own process group, and on the deadline the whole group is killed, so hung downloads do not pile up on the board. When the only errors are slow sources, or a card that is inserted but not mounted, the retry waits 15 minutes instead of 2, so a slow but working board does not start its `curl`-heavy listings every few minutes against GitHub's 60 requests an hour.

    </details>

- **An image parked on the card did not appear in the list for up to 30 minutes.** A successful park now marks the cached list stale, so the next look starts a refresh. <small class="tp-tag">bmcd 2.42.2</small>
- **The message for parking an image with no card said "Insert one, or upload without parking", which was a dead end in the web interface.** It now says the image was not saved because no SD card is mounted, and that installing directly is `tpi firmware upload` without `--park` or the interface's install option. <small class="tp-tag">bmcd 2.42.2</small>
- **Concurrent requests with nothing cached each started their own firmware check.** A request that finds the list empty now waits for the one refresh instead of starting another. <small class="tp-tag">bmcd 2.42.2</small>
- **The (i) notes pointed at a dead docs host.** Every "Read more" link on the Firmware, Fan, Console and Nodes pages led to `turing.excavador.xyz`, which answers an error; they now go to turingpi.xyz, and the two Console notes land on the note instead of the top of the page. A lint rule rejects the old host. <small class="tp-tag">BMC-UI 4.4.0</small>
- **The Grafana dashboard's description linked to the dead docs host.** It now points at the [metrics reference](/reference/metrics/). The dashboard is not part of the image. <small class="tp-tag">v2.47.0</small>
- **`GET /api/bmc/info` says whether an SD card is mounted.** The `SD card` entry in `storage` gains `mounted`, decided by the same mount-point test the park and staging code use. <small class="tp-tag">bmcd 2.42.2</small>

    <details class="note">
    <summary>The whole entry</summary>

    Before, a client could only guess, by noticing that the entry's sizes equalled the BMC's. Additive: the `BMC` entry has no `mounted`, and the `SD card` entry is present under the same rule as before. The sizes are not a statement about a card while `mounted` is false; read the new field instead.

    </details>
